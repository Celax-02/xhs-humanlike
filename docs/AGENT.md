# 用 AI Agent 运行本项目

这个项目很适合托管给一个能执行 shell 的 AI Agent（Claude Code、Codex CLI、Cursor、WorkBuddy 等）：
脚本本身就是"读界面 → 决策 → 注入事件"的循环，Agent 只需要负责**准备环境、启动它、看日志、按需调参**。

下面是可直接复制的提示词。每条都写成自包含的 —— Agent 看不到你我的这段对话，所以背景、路径、验收标准都写在提示词里。

---

## 前提：有两件事 Agent 替你做不了

1. **手机上点「允许 USB 调试」**。那个弹窗只认手指，Agent 点不了（点了也没权限）。
2. **解锁手机**。锁屏密码同理，任何 adb 命令都解不开。

所以流程永远是：**你先把手机插好、解锁、允许调试 → 再让 Agent 接手**。

另外 Agent 需要在项目目录下执行命令。如果你用的 Agent 需要指定工作目录，先 `cd` 到仓库根目录再启动它，或者把路径写进提示词。

## 场景一：首次搭建并验证（推荐第一次用这个）

> 我在 `~/git/xhs-humanlike` 目录下有一个用 adb 模拟真人刷小红书的 Python 项目。
> 手机已经用 USB 连上电脑、已解锁、已授权 USB 调试。
>
> 请按顺序做这几件事，每步都要贴出实际输出给我看：
>
> 1. 读一遍 README.md 和 doctor.py，确认你理解了它的运行方式。
> 2. 检查这台电脑上 adb 是否可用。如果 `adb version` 失败，帮我找到 platform-tools
>    的位置（macOS 常见于 `~/Library/Android/sdk/platform-tools/adb`）。
> 3. 运行 `python3 doctor.py`，把每一项的结果解释给我听。如果有 ✘，先别急着修，
>    把问题和你的建议告诉我。
> 4. 如果自检全部通过，跑一次 `python3 xhs_auto.py --dry-run -t 2 --verbose`，
>    这会连设备读界面但不真的操作手机。确认它能识别到笔记卡片。
> 5. 上面都成功后，正式跑 3 分钟：`python3 xhs_auto.py -t 3 --like 0.03 --fav 0.01`，
>    跑完把日志和统计发我。
>
> 注意：不要试图 root、不要安装任何东西到手机上、不要修改小红书的数据。

为什么先用 `--dry-run`：它会走完整个观测和决策流程，只是不注入触摸事件。如果节点树读不到，`--dry-run` 阶段就能暴露，不用等到真的开始点。

## 场景二：日常跑一场

> 在 `~/git/xhs-humanlike` 目录下，用 adb 跑一场拟人化的小红书浏览：
>
> ```bash
> cd ~/git/xhs-humanlike
> python3 xhs_auto.py -t 20 --like 0.03 --fav 0.01
> ```
>
> 这是一个 20 分钟的后台任务，脚本会自己控制手机刷帖子。请你：
>
> - 在后台启动它，不要阻塞
> - 每 3~5 分钟看一次输出，确认没有异常（比如连续报错、卡在同一屏、
>   误触进直播间、退出到桌面）
> - **如果看到手机屏幕锁了、或者小红书退到桌面了，立刻停下来告诉我**，
>   这两个情况脚本自己恢复不了，需要我手动处理
> - 跑完把完整的帖子清单和最后的统计行贴给我
>
> 中途我说"停"就用 Ctrl+C 或者杀掉进程，然后执行
> `adb shell svc power stayon false` 把屏幕常亮恢复掉。

## 场景三：改参数再跑

> 在 `~/git/xhs-humanlike` 里，把刷小红书的节奏改一下再跑。
>
> 我的要求：
> - 点赞概率降到 1.5%，收藏 0.5%
> - 评论区翻得更浅一些，现在翻太深了
> - 整体节奏慢一点，不要一直在快划
>
> 请先读 docs/BEHAVIOR.md 找到对应的参数，告诉我你打算改哪几行、改成什么值、
> 为什么这么改。等我确认后再改、再跑 15 分钟。

关键在于**先解释再动手**。行为模型的参数是相互耦合的（比如调低精力衰减会同时影响阶段权重、停留时长和评论深度），让 Agent 说清楚它改的每一个数字会影响什么。

## 场景四：让 Agent 改行为模型

> 项目在 `~/git/xhs-humanlike`，是一个用 Python + adb 模拟真人刷小红书的脚本，
> 核心逻辑在 `xhs_auto.py` 的「注意力模型」和「行为段」两节，设计思路见 docs/BEHAVIOR.md。
>
> 我想加一个新行为：[描述你要的行为，例如"看到一个帖子有超过 10 张图时，
> 逐张翻完而不是只翻两三张"]。
>
> 请：
> 1. 先读 docs/BEHAVIOR.md，理解现有模型为什么这么设计（尤其是为什么要用对数正态
>    和指数分布，而不是均匀分布）
> 2. 说明你的改动会落在哪个函数、怎么和现有的 energy 状态配合
> 3. 改完后用 `python3 -m py_compile xhs_auto.py` 检查语法
> 4. 用 `--dry-run --seed 42 -t 2 --verbose` 验证新分支会被触发，把日志给我看
> 5. 不要改动触摸注入部分（`drag()` / `tap()`），那部分验证过是稳定的

第 5 条很重要：`drag()` 里的分段和缓动参数是实测调出来的，Agent 很容易"顺手优化"然后破坏手感的连续性。

## 场景五：出问题了

> `~/git/xhs-humanlike` 跑不动了，症状是：[描述症状]。
>
> 请按这个顺序排查，每步都贴输出：
> 1. `adb devices -l` —— 设备还在不在、是不是 `device` 状态而不是 `unauthorized`
> 2. `python3 doctor.py` —— 哪一项 ✘
> 3. `adb shell dumpsys window | grep mCurrentFocus` —— 当前前台是什么
> 4. `adb shell uiautomator dump /sdcard/t.xml && adb pull /sdcard/t.xml /tmp/t.xml`，
>    然后看 `/tmp/t.xml` 里有没有 `content-desc` 以「笔记」开头的节点
>
> 如果是第 4 步读不到节点，说明小红书改版了无障碍描述格式，需要改
> `feed_notes()` 里的正则。改之前先把你看到的实际 `content-desc` 原文发我。

## 给 Agent 的边界（建议写进它的规则里）

如果你用的 Agent 支持项目级规则文件（`CLAUDE.md`、`AGENTS.md`、`.cursorrules` 等），可以把下面这段放进去：

```markdown
## xhs-humanlike 项目约束

- 只通过 adb 标准输入事件操作手机：input tap / input motionevent / input keyevent。
  不 root、不 adb remount、不修改 /data 下任何文件、不安装任何 App 或模块。
- 不读取、不导出小红书的私有数据（/data/data/com.xingin.xhs）。
- 遇到验证码、滑块、「检测到异常行为」提示，立刻停止脚本并告知用户，
  不要尝试自动通过验证。
- 点赞/收藏概率不要超过 5%。用户没明确要求时用默认值 0.03 / 0.01。
- 单次运行不超过 30 分钟；用户说停就立刻停，并执行
  `adb shell svc power stayon false` 恢复屏幕设置。
- 修改行为模型前先读 docs/BEHAVIOR.md，说明改动理由后再动手。
  不要修改 drag() / tap() 的注入逻辑。
```

## Agent 的验收清单

跑完之后可以用这几条判断这场跑得好不好：

| 检查项 | 合理范围 | 说明 |
|---|---|---|
| 单篇平均停留 | 15~30s | 低于 10s 说明节奏太快，高于 45s 说明太慢 |
| 点开 / 划过 比例 | 1:2 ~ 1:5 | 20 分钟大约 80~120 屏、20~35 篇 |
| 行为段分布 | 四种都出现过 | 只有一种说明权重或 energy 有问题 |
| 点赞次数 | 0~3（20 分钟） | 明显更多就把 `--like` 调低 |
| 异常 | 无锁屏、无掉到桌面、无进直播间 | 出现任一说明兜底逻辑需要检查 |

如果日志里从头到尾没出现过 `休息` 段，或者 `精力` 一直停在 0.1 附近，那是 energy 的衰减项写错了，不是运气问题。

---

## 一点提醒

Agent 很适合做**重复的、需要看日志判断的**事情（跑一场、盯异常、改参数再跑）。但它不适合替你做风险判断 ——
"这个频率会不会被风控"、"这个用法符不符合平台协议"，这类问题它给不出可靠答案，也不该由它决定。

所有涉及账号的动作，最终按下回车的那个人应该是你。
